## 1. 本目录是什么

只有一个文件 `obsidian.ts`：`obsidian` 包在 Node/Vitest 环境下的手写最小替身。`vitest.config.ts` 把模块名 `obsidian` 别名到它（见根目录 `AGENTS.md`），所以被测源码里的 `import ... from "obsidian"` 实际加载的是这个文件，而不是真实的 Obsidian API。
它只提供"让源码能被导入、让纯逻辑能被执行"的最小实现，不模拟 Obsidian 的界面或事件系统。

## 2. 直属文件

- `obsidian.ts`：导出清单与行为如下。
  - 值导出：`moment`（可调用工厂，附带 `unix()` 与 `duration()`；`diff()` 恒为 0、`format()` 恒为 `""`、`duration().isValid()` 为真、`asDays()` 为 1）、`Platform`、`Notice`、`TAbstractFile` / `TFile` / `TFolder`、`Plugin`、`Menu`、`Scope`，以及空类 `ItemView`、`MarkdownView`、`WorkspaceLeaf`、`PluginSettingTab`、`Modal`、`SuggestModal`、`FuzzySuggestModal`。
  - 函数导出：`normalizePath`（反斜杠转 `/`，合并重复 `/`）、`getLanguage`（维护版加的，恒返回 `"en"`；`src/syncProblems.ts` 的 `syncLanguage()` 靠它选文案语言）、`setIcon`、`setTooltip`（空操作）、`debounce`、`requestUrl`。
  - 仅类型导出：`EventRef`、`RGB`、`EditorPosition`、`Editor`（只有 `getCursor`）、`HoverParent`、`HoverPopover`、`ViewStateResult`、`MenuItem`、`TextComponent`、`DataAdapter`、`FileSystemAdapter`、`Vault`（只有 `getAbstractFileByPath`）、`App`（`vault`、`workspace.getLeaf / trigger`、`viewRegistry.getTypeByExtension`）、`Debouncer`。

## 3. 子目录导航

无直属子目录。

## 4. 本层约束 / 约定 / 禁忌

- `Platform` 是普通可变对象，默认全部是桌面值：`isDesktop`、`isDesktopApp` 为 `true`，`isMobile`、`isMobileApp`、`isMacOS`、`isWin`、`isIosApp` 为 `false`。要走移动端分支的用例必须自己改属性并在结束后还原；该文件本身不提供切换手段。
- `debounce` 是手动触发版本：调用只记录参数并返回同一个 debouncer，不起定时器；回调只在 `.run()` 时执行（`.cancel()` 清掉待执行参数）。依赖真实延迟触发的代码在测试里不会自动执行。要断言传给 `debounce` 的延迟，用例用 `vi.mock("obsidian")` 把它包成 `vi.fn(actual.debounce)`（`tests/automaticsManager.test.ts`）。
- `requestUrl` 恒返回 `{ status: 404, headers: {} }`，没有 body；需要别的响应或网络行为时用例必须 `vi.mock` / spy 覆盖。
- `Notice` 只保存 `message` 与 `timeout`，`hide()` 为空操作，另有维护版加的 `messageEl`（一个只有空 `addEventListener` 的对象，`SyncSupervisor` 给通知挂点击监听时用）；要断言弹了什么通知，用例用 `vi.mock("obsidian")` 派生一个 `Notice` 子类来记录参数（`tests/syncSupervisor.test.ts`）；`Menu` 只有空的 `showAtPosition()`；`Scope` 只有空的 `register()`。
- `Modal`、`ItemView`、`MarkdownView`、`WorkspaceLeaf`、`PluginSettingTab`、`SuggestModal`、`FuzzySuggestModal` 都是没有任何成员的空类（没有 `open / close / contentEl / registerEvent` 等）。继承它们的 UI 类可以被 import，但不能真正实例化后使用；现有测试的做法是整模块 mock（如 `vi.mock` 掉 `GeneralModal`），或绕过构造函数（`Object.create(X.prototype)`）。
- `TFile.setPath()` 与 `TFolder` 构造函数调用了 `Array.prototype.last()`——这是 Obsidian 注入的全局扩展，不是标准 JS；使用这两个类的前提是运行环境里已经有该扩展（Node 下由全局 setup 文件补上，见上级 `tests/.frac.md`）。
- 这里导出的类型是为了让别名后的导入可编译，范围比真实 `obsidian` 窄得多（例如 `Vault` 只有 `getAbstractFileByPath`）。测试里需要更多成员时，用 `as unknown as` 强转的假对象，或在此文件补最小成员，而不是引入真实的 `obsidian` 包。
- 源码新引用了此处没有导出的 Obsidian API 时，要在这里补一个最小实现；缺失的名字在运行时读到的通常是 `undefined`，只会在被使用的那一刻才失败。

## 5. 什么时候需要下钻

- 源码新增 `obsidian` 导入、或某个用例因 `Platform`、`debounce`、`requestUrl`、`Notice` 的行为不符合预期而失败：先读本文件，再决定是改 stub 还是在用例里局部覆盖。
- 想知道哪些测试需要伪造 plugin / vault：看 `tests/helpers/.frac.md`（`createFakePlugin`、`createNodeVault`），那里的假对象与这里的 `App` / `Vault` 类型并不共享定义。
