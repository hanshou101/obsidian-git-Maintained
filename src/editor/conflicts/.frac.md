## 1. 本目录是什么

编辑器内的合并冲突解决 UI：在笔记正文里识别 `<<<<<<<` / `=======` / `>>>>>>>`（可带 `|||||||` diff3 base）冲突块，给标记行染色、在每个冲突块上显示 Keep ours / theirs / both / base 按钮，并提供「整文件一键处理」入口。
分三层：`model.ts` 纯文本解析（无 CodeMirror/Obsidian 依赖）→ `actions.ts` 用 `EditorView.dispatch` 改文档 → `view.ts` 的 CodeMirror 扩展（StateField + 装饰 + 面板）。对外入口是 `view.ts` 导出的 `conflictExtensions`，需由上级把它注册为编辑器扩展。不调用任何 Git 操作，解决后是否 `git add` 不在本目录处理。桌面/移动共用，只在摘要 UI 的呈现方式上按 `Platform.isMobile` 分叉。

## 2. 直属文件

- `model.ts`：类型 `ConflictChoice = "ours" | "theirs" | "base" | "both"`、`ConflictMarker`、`ConflictBlock`（`from/to` 为整块范围；`ours/theirs/base` 文本；`markers` 是各标记行范围；`oursRange/baseRange/theirsRange` 是内容区范围），函数 `parseConflictBlocks(text)` 与 `resolveBlockText(block, choice)`。
  - 标记用行首锚定的正则：恰好 7 个 `<` / `|` / `=` / `>`，后面要么行尾要么空格/制表符加任意文本（如 `<<<<<<< HEAD`）。按 `\n` 切行，不处理 `\r`：喂入带 CRLF 的文本时标记行匹配不上（编辑器内 `doc.toString()` 已是 `\n`，现有调用方不受影响）。
  - 解析：遇到 START 后向下找第一个 SEPARATOR（途中第一个 BASE 记为 base）；再向下找 END，若先遇到另一个 START 则放弃这一块；缺 SEPARATOR 或 END 的块被静默跳过。块的 `to` 在非文件末尾时多包含一个换行；`ours`/`theirs`/`base` 文本都包含各自最后一行的换行。
  - `resolveBlockText`：`both` = `ours + theirs`；对没有 base 的（两路）块选 `base` 会抛 `Error("Cannot keep the base of a two-way conflict")`。
- `actions.ts`：`resolveConflict(view, block, choice)` 用一次 `dispatch` 把 `[block.from, block.to]` 换成 `resolveBlockText(...)`；`resolveAllConflicts(view, choice)` 重新 `parseConflictBlocks(view.state.doc.toString())` 并把所有块放进同一个 transaction（一次撤销即可还原）。两者结束都 `view.focus()`。`resolveAllConflicts` 以 `base` 调用且存在两路块时会在 dispatch 之前抛错，UI 层靠只在全部块都有 base 时才显示 "Keep all base" 来避开。
- `view.ts`：CodeMirror 侧实现，导出 `conflictBlocksField`（`StateField<readonly ConflictBlock[]>`）、`conflictMarkersField`（`StateField<DecorationSet>`，通过 `EditorView.decorations.from` 提供装饰）、`conflictExtensions = [conflictBlocksField, conflictMarkersField, conflictPanel]`。
  - `conflictBlocksField` 仅在 `editorLivePreviewField` 为真（即 Live Preview，Source 模式下恒为空）且文本包含 `<<<<<<<` 时才解析；只在 `docChanged || reconfigured` 时重算。
  - 装饰：每个标记行加行装饰 `git-conflict-marker-line`（首个标记另加 `-ours`，最后一个另加 `-theirs`）与 mark 装饰 `git-conflict-marker`；头标记行末尾插入 `ConflictButtonsWidget`（`side: 1`，按钮 Keep ours / theirs / both，有 base 时加 Keep base，点击调 `resolveConflict`）；ours/base/theirs 内容区按行加 `git-conflict-ours-line` / `-base-line` / `-theirs-line`（空区间跳过）。按钮是 Obsidian `ButtonComponent`，class 含 `clickable-icon nav-action-button git-conflict-choose-<choice>`，样式不在本目录定义。
  - 摘要 UI（`renderConflictSummary`：`N conflict(s) in file` + Keep all ours/theirs/both，且全部块都有 base 时多一个 Keep all base，点击调 `resolveAllConflicts`）：桌面用 `showPanel` 顶部面板 `ConflictPanel`（`!Platform.isMobile` 且有冲突才出现，`docChanged`/`reconfigured` 时重新渲染）；移动端改为在位置 0 插入 block widget `ConflictSummaryWidget`（`side: -1`，`eq` 只比较 count 与 hasBase）。

## 4. 本层约束 / 约定 / 禁忌

- `parseConflictBlocks` 是整个功能的单一事实来源：`view.ts` 的字段重算和 `actions.ts` 的批量处理都调用它；改标记语法或块边界（`from/to`、各 `Range`）会同时影响装饰位置、按钮替换范围和批量替换。
- 冲突 UI 只在 Live Preview 里出现，这是 `computeBlocks` 的显式门禁；要在 Source 模式支持必须改这里，而不是改装饰。
- 解决冲突只 `dispatch` 文档改动：本目录不写磁盘、不 stage、不刷新 Git 状态。
- 桌面与移动的摘要入口互斥（面板 vs block widget），改摘要内容时两处共用 `renderConflictSummary`，不要在只有一端的分支里单独改文案。
- 按钮文案是硬编码英文字符串（Keep ours / Keep theirs / Keep both / Keep base / Keep all ...），class 名 `git-conflict-*` 需要与 CSS 保持一致。
- `ConflictButtonsWidget.eq` 只比较 `from/to/ours/theirs/base`，恰好是 `resolveConflict` 用到的全部字段；若让动作改为依赖 `markers` 或各 Range，必须同步扩展 `eq`，否则 CodeMirror 会复用仍持有旧 block 的 widget。

## 5. 什么时候需要下钻

- 改冲突识别规则（diff3、嵌套、CRLF）：只读 `model.ts`。
- 改按钮 / 面板 / 装饰表现或平台差异：读 `view.ts`，并确认 CSS 中的 `git-conflict-*` 类。
- 改解决动作（撤销粒度、解决后聚焦、解决后 stage）：读 `actions.ts`，必要时到上级 `src/editor` 看扩展是如何注册与启用的。
